## 唯一权威资产

- 本模块（`prompts/ai-daily/modules/editorial-authority.md`）是当前中文 AI 日报的唯一权威资产。
- 如果它与其它 prompt 模块、`docs/*.md`、历史 ROI 清单、旧 runbook、旧任务模板或历史日报说明冲突，以本模块为准。
- 同一板块如果出现新旧两版要求，只执行这里更新后的版本；旧文档只作归档参考，不再参与当前合同裁决。

### 迭代维护机制

- 这份资产不是一次性说明，而是后续内容改版、板块迭代和质量修正的唯一回写面。
- 只要发生板块增删改名、读者口径调整、选题阈值变化、公开写法变化、质量门更新、good case / bad case 更新或 ROI 重排，就必须同步回写这里。
- 同一章节如果出现新旧两版要求，后写覆盖前写；不要保留“旧要求可能还有效”的模糊状态。
- 非平凡内容迭代至少要同步更新四处：`本轮修改清单`、`Good Case`、`Bad Case`、`迭代历史`。
- 旧文档可以保留为归档证据，但当前执行口径只认这份资产，不做并行裁决。

### 当前定位

- 这份日报不是只给工程师看的技术快报，而是更接近内容/产品型长日报。
- 目标读者是同时关心内容、产品、平台、策略与工程的一线从业者，包括产品经理、内容负责人、平台负责人、研究/工程负责人和资深开发者。
- 公开正文要回答的是：今天最值得知道的 AI 与科技变化是什么，核心事实、边界和来源在哪里；不要把入选条件、执行过程、读者画像或空泛启示写给读者。

### 当前主板块

- `summary` / hero：写成编辑导语，先讲今天主线，不写生产过程，不写“本次筛了多少条”。
- `main_items`：目标为 5-30 条短新闻流；5 是低信号日最低值，5-20 是常规舒适区，21-30 是高信号日可接受区间。按公共 AI 重要性、科技新闻声量、大厂名气和泛 AI 热点排序，不按用户个人工作直接相关性排序，也不按抓取偶然性排序。每条只展示标题、2-3 句/行可追溯事实概括和来源链接。
- `hot_blogs`：对外固定显示为“热门博客”，承载观点、产品拆解、平台策略、内容生态、组织方法、创作者工作流、高质量工程深读、访谈和播客。
- GitHub Trending：保留完整 Top 10；要解释项目是什么、解决什么问题、为什么值得看，但它不再主导整份日报的主线。
- Builder / X / 社区线索：只保留争议、分歧和早期信号，不做帖子搬运流。
- OpenRouter / Artificial Analysis / 榜单类板块：公开页优先展示从 DOM、JSON 或页面文本解析出的结构化表格，例如排名、模型、供应商、分数/token、周变化；整页截图、浏览器截图或 viewport 截图不得作为公开正文主内容。

### 选题升降级

- 默认不过稿：单一厂商的轻量合作、区域开放、例行上架、preview access、普通 PR 稿、重复发布、无明确能力边界变化的小更新、无真实工作流变化的轻运营项。
- 模型发布优先抓“原始能力变化”：实验室/模型方对模型关系、安全边界、访问权限、价格和能力范围的说明优先于云平台、IDE、Copilot、网关或 marketplace 上架公告；后者只能作为同一条新闻的可用性补充。
- 只有当变化会影响能力边界、分发渠道、价格/配额、组织动作、内容供给、创作者工作流或开发工作流时，才允许升格。
- 英伟达、小模型、新显卡之类的更新，只有在“重大模型 / 重大硬件 / 突破性能力 / 行业级影响”时才进入主线。
- 主线不得收窄成“和我工作直接相关”的私人工具清单；大厂模型、平台政策、AI 产品、算力、监管、资本、内容产业、开发者生态和广义科技热点都按公共重要性参与排序。

### 语言和禁区

- 说人话。不要写工作汇报腔、评审腔、模板判断句。
- 禁止把机器日志、shell 超时、source audit 过程、候选池写回、抓取成功/失败说明写进公开摘要、主体、热门博客或公开建议区。
- 禁止 `读者应重点核对`、`判断点`、`把它当作……信号`、`后续继续跟进` 这一类模板句。
- 主体、热门博客和社区线索不写重复的“为什么重要 / 后续跟进 / 风险提示 / 启示 / 影响”空话，除非有具体、可验证的边界说明。`why_it_matters`、`reader_relevance`、入选理由、候选分数和 watch-next 只可作为内部兼容元数据，不得成为公开正文。

### 覆盖与保留

- 必保留：GitHub Trending Top 10 完整榜单。
- 内部报告必保留：coverage window、自检、`quality_status` 和 `source_audit` 的结构化记录；公开页只显示读者可理解的短缺口说明，不公开内部审计字段。
- 不再单独公开：`model_releases`、`今日值得关注的项目`、`项目 highlights`、`国内动态`空栏目。
- 国内/中文内容要并入现有栏目，保证可见，但不为了“国内”再单开一个空导航。
- 图片不是 KPI；无图日报可以通过。公开正文只展示尺寸、语义、可读性合格的原文内部图片资产或结构化表格；tiny icon、favicon、logo、头像、装饰图、整页截图和不可读截图不得作为主内容展示。
- 公开日报与内部报告严格分离：公开页默认隐藏 source audit、self-check、ledger、degradation、candidate diagnostics、执行命令和失败案例；这些只保留在 JSON、质量报告或交接材料中。
- 公开日报渲染固定走 `.codex/skills/effective-interact` 的 `pre-rendered` 模式；`reports-data` 保留完整内部报告，`docs/data` 只保留读者安全字段。

### Good Case

- 主线新闻按公共 AI 重要性排序，覆盖大厂模型、产品、平台、算力、监管、资本、内容产业和开发者生态；每条用 2-3 句/行讲清事实和来源，不写入选理由。
- “热门博客”收录的是高信息密度的深读、拆解、访谈或播客，不是普通技术博客堆叠；读完能带走观点、方法或能力地图。
- GitHub Trending 条目不只翻译仓库描述，而是说明它解决什么问题、适合什么场景、为什么今天值得看。
- 中文 / 国内内容来自一手公告、原文访谈、原始演讲或可回溯信源，能自然并入现有主线，而不是额外挂一个空栏目。
- Builder / X / 社区线索只在存在明确争议、分歧或早期信号时出现，并且能指出争论点到底是什么。
- 榜单页把 Top 10、供应商、分数/token、周变化等结构化数据展示成表格；图片只在能清晰增强理解时出现。

### Bad Case

- 把 preview access、普通 PR 稿、例行上架、轻量合作或没有能力变化的小发布硬写进主线。
- 把“筛了多少条”“抓取成功”“source audit 显示”“shell 超时后重试”这类机器执行痕迹写进正文。
- 用“读者应重点核对”“把它当作一个信号”“后续继续跟进”之类模板句代替真实判断。
- 把 Builder / X 原帖做成搬运流，只复述帖子内容，不交代争议点、边界或实际意义。
- 为了看起来全面，保留 `模型发布`、`今日值得关注的项目`、`项目 highlights`、`国内动态` 这类空栏目或弱栏目。
- 主体只有少数几条新闻，或把每条写成“为什么重要 / 启示 / 读者应该关注”的泛化说明，真正事实概括很短。
- 把 OpenRouter、Artificial Analysis 或类似网页整页截图直接放进正文，导致手机端不可读。
- 为了凑图展示 favicon、logo、头像、小图标、装饰图或不可读截图。
- 把 `source_audit`、`self_check`、`candidate_id`、`quality_status`、`remediation`、`parsed_count` 或“来源 第三方报道 / 今天进入 GitHub Trending Top 10 / 这条动态主要围绕 / 序号 1”这类生成痕迹写入公开页。

### Forbidden Case

- 没有原始来源的数字、结论、判断和“行业都在关注”。
- 媒体二手转述、社区传闻或聚合站摘录直接升格为主线事实。
- 机器日志、source audit 过程、候选池回写、抓取成败说明、发布器状态说明进入公开正文。
- 明显 AI 腔、工作汇报腔、评审腔、空泛“为什么重要”尾巴混入 `summary`、主体或“热门博客”。
- 用个人工作相关性排除公共 AI 重要新闻、大厂动作或泛 AI 热点。
- 整页截图、浏览器截图或 viewport 截图作为公开正文主要信息载体。
- 公开页暴露 ledger、自检、source audit、候选诊断、执行命令、质量门失败详情或失败案例复盘。
