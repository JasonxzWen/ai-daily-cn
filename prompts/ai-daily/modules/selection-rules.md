## 选择规则

- 主体信息默认按 10 条组织，允许 8-12 条；每条约 80-120 个中文字符，用 2-3 个短 bullet 分点汇报，并用 `**加粗**` 和 `==高亮词==` 标出实体、变化、限制或关键结论。`==高亮词==` 是正文文字强调，不是 tag/chip。不要为了凑数加入低质量内容。
- 读者不是只看工程实现的人，而是同时关心内容、产品、平台、策略与工程的一线从业者。日报要接近内容/产品型长日报：不仅回答“技术上有什么更新”，还要回答“哪些变化会影响产品判断、内容供给、平台分发、组织动作或开发工作流”。
- `main_items` 是公开事实主线，只能使用官方、一手、论文、GitHub 或多源确认材料；`model_releases` 仅保留为历史兼容的结构化字段，不生成公开栏目。普通媒体、微信公众号、自媒体、聚合摘要、播客观点和 X 热点不得包装成事实报道主体。
- 非一手内容可以进入 `hot_blogs`、`projects`、`builder_observations` 或 `community_leads`，但必须填写 `source_level`、`verification_status`，并至少填写 `verification_note` 或 `risk_note`。融资、估值、价格、benchmark、安全事故、监管、模型能力仍需一手或多源确认。
- `main_items` 每条必须填写 `why_it_matters` 或 `reader_relevance`，让读者知道它和内容生产、产品路线、平台分发、组织动作、工程实践、工具选择、迁移风险、成本或上线节奏有什么关系。
- 同一事件只保留一条，优先官方或原始来源。
- 去重和新鲜度优先于丰富度；严格筛完只剩 2-3 条也可以发布，不要用旧内容补满页面。
- 低价值小新闻不过稿：单一厂商的轻量合作、区域开放、例行上架、preview access、普通 PR 稿、重复发布、无明确能力边界变化的“小更新”、无真实工作流变化的轻运营项，默认不进 `main_items`。只有当它改变能力、分发、价格、组织、内容生态或真实工作流时才升格。
- 所有资讯收集都必须先和 `reports-data` 中最近至少 7 个日报日的日报正文与候选池比较：先按 URL 去重，再按同一事件、标题、厂商、来源主题和发布时间去重；重复项不得换标题重新包装。
- 最近 7 天已经进入任何日报正文或项目/博客/模型区的 URL，默认不能再次进入 `main_items`。
- 如果同一来源在前几天已出现，只有出现新的 dated release、版本、政策、价格、可用范围、基准或工程结论时才能再次入选，并必须在候选池 notes/evidence 中说明新增变化。
- 同一 URL 不能在同一天同时进入 `main_items` 与 `hot_blogs` 重复包装；新草稿默认保持 `model_releases: []`，模型类重大动态统一写入 `main_items`。
- 48 小时外的内容不能进入 `summary` 或 `main_items`；如确有必要，只能作为补充/背景线索，且每天最多 1 条。
- 同一厂商同日或同一 48 小时窗口内的多条小更新默认合并为一条厂商动态；只有当它们分别改变不同工程工作流、来源和风险面时才拆分。
- AI 日报可以收录广义科技、大厂动态和行业趋势，但必须和 AI 生态有明确关系：例如模型/agent 供给、开发者工具、云和算力、芯片、平台政策、浏览器/OS 分发、监管、融资并购或企业采购变化。普通消费科技新闻、泛商业评论和无工程影响的股价波动不入选。
- `model_releases` 是历史兼容字段，新草稿默认空数组，不要用它生成公开栏目。新模型、新模型家族、新权重、官方 API 正式上线或实质模型卡更新，只有影响能力边界、工具选择、成本或上线节奏时才进入 `main_items`。第三方网关上架、产品内开放、preview access、区域/账号可用、状态页 incident/恢复和短时配额变化默认是轻量运营项，写入 `community_leads`；只有影响生产迁移、成本边界、企业采购路径或上线排期时才升格为 `main_items`。
- `hot_blogs` 在公开页显示为“技不止术”，不计入主体信息数量；它不是新闻凑数池，而是承载观点、产品拆解、平台策略、内容生态、组织方法、创作者工作流以及高质量工程/研究/agent/eval/design 文章、访谈和播客的深读区。
- GitHub Trending 进入独立 `github_trending` 板块，默认展示 Top 10 仓库并带排名变化和 star 变化 tag；它不是主体信息凑数池。只有经过额外 release、README、近期 commit 或工程影响核验的项目才再进入 `projects`，但公开页面只能在匹配的 GitHub Trending Top 10 条目上增加 `项目 highlight` tag 和行内用途说明；不单独生成“今日值得关注的项目”板块、“项目 highlights”子标题或额外项目列表。
- 访谈和播客只有在包含明确工程实践、技术路线、成本结构、模型/agent 经验或组织实践时才收录；泛泛宣传只作为社区线索。
- Product Hunt 和新产品榜单只作为候选入口，入选 `projects` 前必须说明领域、作用和可验证信号；公开展示时只能作为匹配 GitHub Trending Top 10 条目的 `项目 highlight` tag，而不是独立项目区。
- AI 开发工具的计费、配额、成本归因、usage dashboard、Service Quotas、seat/usage-based billing 和 credit 变化属于常规跟踪项；影响开发者工作流、团队预算、上线容量或采购口径时可进入 `main_items`，否则进入 `community_leads`。
- Builder 观察和社区线索放在独立区域，不计入主体信息。Builder 观察只选能拿到原帖/原文连续摘录的观点，必须写 `original_text` 和逐句忠实的 `translation`；候选足够时公开入选 5-20 条，不要只挑 2-3 条；不要把原帖改写成“我方观察”或观点摘要。
- 国内/中文动态不能只停留在候选池或信源审计里：当中文科技媒体、公众号输入或国内厂商官方源合格候选不少于 3 条时，公开内容中至少保留 3 条国内相关内容，并优先分布到现有 `main_items` 分组（AI 资讯 / 大厂与政策 / 产品与开源 / AIGC 动态）、`hot_blogs`、`github_trending` 或 `community_leads`。已回到官方/一手来源且满足事实主线标准的，优先进入 `main_items`；未回源或涉及融资、营收、估值、benchmark、监管、模型能力等高风险事实的，只能进入 `community_leads`，并标记待官方或多源验证。不要生成独立“国内动态”导航项。
- 对没有一手来源的普通媒体消息、微信公众号、自媒体或聚合摘要，只能降级为社区线索，并标记待验证；不要把普通中介来源写成事实报道实体。用户白名单公众号可用于低风险行业动态和观点分析，但必须标明 `source_level`、公众号名、发布时间、待核验点和风险等级；融资、估值、价格、benchmark、安全事故、监管、模型能力仍需一手或多源确认。
- X 热点只有保留原始 X status URL 时才进入候选；没有原始帖链接的热度摘要必须丢弃或保留在审计 notes 中。
- 融资、商业化和大厂人事/组织变化只有在官方公告或多源证据充分、且影响 AI 供给链或产品路线时才进入主体信息。
- 避免模板化段落，例如“对我们的影响”“工程意义”“启示”“总之”“赛道”“深度融合”“读者应重点核对”“判断点”“把它当作……信号”。
